3. 逐视频补全统计：`bilibili_api.video.Video(bvid=..., credential=...).get_info()['stat']`

### 关键坑：空间列表接口字段有诈
`get_videos` 返回的 vlist 里：
- `video_review` 是**弹幕数**，不是点赞数（名字骗人）
- `review` 恒为 0，**列表接口根本不返回点赞和收藏**

## B站风控实测（决定并发与防护策略）

### 核心结论
**决定性变量是 cookie 有无，不是并发数。**
- 带 cookie：并发 1→12 全通过；10 轮 × 8 并发 = 80 次调用 / 160 个 HTTP 请求，零风控。
- 无 cookie：并发 6 × 5 轮只有 22/30；**降到单线程逐个（间隔 0.3s）仍然只有 3/8**。
  → 说明不是速率问题而是身份问题，降速无效，只能靠 cookie。

无 cookie 时错误表现为 `NetworkException: 状态码 412` + 一段 HTML 页面（不是 JSON）。
补上 cookie 后同一批复测 7/8 通过（剩 1 个是账号本身投稿为 0）。

### 请求放大（容易踩的坑）
`User.get_videos` **内部会先发 1 个请求**去
`https://space.bilibili.com/{mid}/dynamic` 拿 `w_webid`，再发真正的
`x/space/wbi/arc/search`。所以**理论 16 次实际发 32 次**。
`get_access_id` 的 docstring 说"如未过期直接从本地获取"，但实测同实例连续两次
调用仍是 4 个请求 —— **没有复用，每次都重取**。压测时别按理论值估请求量。

### 性能真值
- 8 并发 × 每 UP 2 次顺序调用：1.5 ~ 3.8 秒
- 16 并发（把 order 拆平并发）：1.5 秒 ← 最优
- 曾观测到一次 17.25 秒的离群值，**不是限速**：紧接复测 1.82s，
  静置 10/20/30s 后分别 1.40/1.39/1.18s。B站只是偶发慢响应。
  不要把这种抖动误判成风控并触发降级逻辑。

### 防护建议
- 第一优先级：`get_cookie('bilibili')` 拿 cookie，取不到就直接放弃并明确报错，
  不要用无 cookie 模式硬跑（随机失败还会浪费请求）。
- 并发封顶 8~16，加随机抖动（不要固定间隔，容易形成机器特征）。
- 遇到 412 退避重试：1s → 2s → 4s，最多 3 次。
- 7 天缓存是**最有效的降压手段**，直接消掉重复采集。

## 落地：credibility 模块（内部工具，非子命令）

新增 `src/app/services/credibility/`（619 行），对现有代码只加了两个公开方法
（`GPT.ask` / `UniversalGPT.ask`），其余全是新文件。177 个既有测试全通过。

```
models.py      CreatorProfile / VideoTitle / CredibilityResult / FetchFailure
fetcher.py     并发采集 + 7天标题缓存 + 412退避
assembler.py   标题拼装成证据块（纯本地，0请求0token）
prompt.py      CREDIBILITY_PROMPT 占位（用户手写）
analyzer.py    编排 + 单次LLM调用 + 结论缓存
```

调用方式：
```python
from app.services.credibility import analyze_credibility
r = analyze_credibility(creators=[("名称","mid"), ...], topic="家电选购建议")
print(r.report)
```

### 关键设计决策
- **提示词未填时不发 LLM 请求**：`prompt.py` 保留 `TODO：此处由你手动填入`
  占位标记，`is_prompt_ready()` 检测后直接返回说明。标题照常采集入库，
  所以用户填完提示词重跑时零请求。
- **结论缓存键含提示词哈希**：`{prompt_hash}_{mids_hash}`，
  提示词一改自动失效，不会读到旧结论。这个坑不提前埋进去以后很难查。
- **证据量如实标注**：模型看到的标题条数（上限30）与实际采集条数（可达60）
  在证据块中显式说明，避免模型误判证据量。
- 失败不静默：`FetchFailure` 单独记录并在 report 中如实列出。

### 实测开销（4 个 UP 主）
- 采集 189 条标题，冷启约 3 秒
- 输入证据 5334 tokens + 输出约 1950 tokens
- 二次运行：**0.001 秒 / 0 HTTP 请求**（缓存全命中）
- LLM 判断质量高：准确识别出软广号的品牌反复出现（希亦 16 条里 11 次）、
  敢写缺点的深度号、以及与主题不相关的号（会主动说"不相关"而非勉强评级）
